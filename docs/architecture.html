vision-ocr-batch · architecture

Vision OCR architecture

A Spring Batch job reads scanned forms, asks Azure Document Intelligence what kind of document each one is and what it says, then checks every field against rules from a per-doc-type XML file. A Spring Boot demo app runs the same job in-process and lets reviewers correct what the model got wrong.

  • 2 Maven modules: ocr-batch, ocr-ui
  • 8 job steps, all driven by document status
  • 1 SQL Server schema: ocr
  • 0 Java changes to add a doc type

1 · System context

Two entry points, one job

  • The database is the queue. Every step picks documents by doc_job.status. A crashed or stopped run is launched again and continues where it stopped.
  • Uploads go through the folder. The UI writes the file into data/input/ (or data/input/<DOC_TYPE>/ to skip the classifier) and calls JobTrigger. Ingest then picks it up like any scanned file.
  • Shared database, own schema. Everything lives in ocr, including Spring Batch's BATCH_* tables. The schema scripts only create missing objects.
2 · Job pipeline

docExtractionJob, step by step

StepBeanWhat it does
0 viewDocTypeViewTaskletRecreates one flat view per doc type, ocr.v_doc_<doctype>, with columns from the doc type XML. The only DROP the job ever runs.
1 recoveryRecoveryTaskletApplies pending doc_reprocess_request rows and moves due ERROR documents back to the entry status of the stage that failed.
2 ingestIngestTaskletRegisters new files from input.dir in doc_job. SHA-256 skips duplicates. A sub-folder named after a doc type pre-assigns it.
3 classifyClassifyProcessor → DocumentStatusWriterRuns the custom classifier. Unknown type, several types in one file, or low confidence send the document to REVIEW.
4 extractExtractProcessor → DocumentStatusWriterRuns the doc type's extraction model and stores the fields JSON (and optionally the full response, gzipped) in doc_azure_result.
5 mapValidateMapValidateProcessor → MappedDocumentWriterApplies the doc type rules to the stored JSON (see section 4) and writes doc_field rows and doc_job.extracted_json.
6 housekeepingHousekeepingTaskletClears old full Azure JSON and deletes old history, error and Spring Batch rows, in batches.
7 summaryJobSummaryTaskletLogs counts per doc type and status. Logs never contain field values.

5 · Data model

Tables in schema ocr

The model's value in doc_field is never overwritten. Reviewer fixes go to doc_field_correction, and the views apply them, so downstream systems read reviewed data and corrections survive reprocessing.

Table / viewHoldsWritten by
doc_jobOne row per file: current status, doc type, review reasons, retry state, extracted_json. The work queue.every step
doc_azure_resultEvery successful Azure call. fields_json always; gzipped full response only with results.store-full-json=true. is_current marks the latest.classify, extract
doc_fieldOne row per extracted field, with raw value, cleaned value, confidence, field_status, message.mapValidate
doc_field_correctionFix, confirm and undo actions, keyed by field name. Also the training-data export.demo UI, SQL
doc_status_historyAppend-only audit of every status change: who, when, why.all steps, UI
doc_errorEvery failure: stage, attempt, HTTP status, retryable.writers, ingest

6 · Demo UI

Screens, endpoints and services in ocr-ui

A plain JavaScript single-page app (core.js, app.js, one module per page in js/pages/) calls four REST controllers. Upload, retry-now, reprocess and "run job" all end in JobTrigger.trigger(). The server binds to 127.0.0.1 and has no login; the reviewer name comes from the header field.
